# 片型适配与能力边界：哪些片子该用 Muse，哪些别用

用户原话（2026-11-21）：

> 「muse 的提示词或者生视频 10s 20s … 60s 官方或者其他渠道有没有，或者 GitHub 有没有相关的，
> 因为他的生视频有一些不太一样。然后再来调整技能——**也不是所有类型视频都适合他当前的生视频逻辑**。」

这一节回答三件事：官方到底给了什么、这台机器的生成逻辑是什么、什么片型该用别的方法做。

---

## 一、官方渠道：只有一条，而且我们一直没读完

### 1.1 有没有 GitHub / 提示词库

**没有。** 2026-11-21 实测：

| 找过的地方 | 结果 |
|---|---|
| GitHub 搜 `muse-video`、`muse-video-60s` | 无对应仓库。`baoge2026/muse-video-skill` 就是我们自己这份 |
| Bing / DuckDuckGo 搜 `"muse-video-60s"` | 命中的全是 Meta 的「Muse AI Agent」，与视频模型无关 |
| 网关 `router.yizzav.com` 的 `/docs/models/muse-video-*` | 是 New API 的 SPA 路由，正文就是下面那段模型描述，没有更多 |
| 网关 `/openapi.json`、`/v1/openapi.json` | 无公开 spec |
| 网关 `/api/models`、`/api/models/search` | 需要用户 JWT，密钥调不通 |

**结论：`muse-video-*` 是网关自己的别名，不是某家模型的原名。** 所以不存在"官方提示词库"这种东西——
唯一的官方文档就是网关 `/api/pricing` 里每个模型的 `description` 字段。

### 1.2 官方原文（`muse-video-60s`，其余档位同文，只改秒数）

> 适合用途｜有声成片总长不超过 60 秒，原生 720p、每秒 24 帧。可以新生成，也可以从较短视频的最后一帧接着写。
> · 使用注意｜续写时 `reference_videos` 只传 1 段公网 MP4。`duration` 是成片总秒数，不是只续写的秒数，
> 而且必须比源片至少长 1 秒。不能靠续写改风格。写实暴力、枪械或爆炸可能生成失败。
> 可传 `style_preset`、`skill_preset`、`custom_style`、`custom_skill`、`mute_voice`、`script`。

### 1.3 这段话里有六个参数，本技能一个都没用

| 参数 | 官方怎么说 | 它可能解决什么 | 状态 |
|---|---|---|---|
| `reference_videos` | 续写时只传 1 段公网 MP4；`duration` 是**成片总秒数**，必须比源片至少长 1 秒；不能靠续写改风格 | 原生续写。现在 7.5-3 那套「抽末帧补拍 10 秒 + ffmpeg concat」可能可以直接用平台做 | **未验证** |
| `script` | 可传 | 如果它是独立的台词/剧本字段，就绕开了「台词必须写进 prompt 且由画面里有没有人说话驱动」这个大坑 | **未验证，价值最高** |
| `mute_voice` | 可传 | 关掉原生人声 → 画面与配音彻底解耦 → 智凌 TTS 后期配音成为正规路径，不再是"两路人声打架"的补救 | **未验证，价值次高** |
| `style_preset` | 可传 | 官方风格预设，比自己写风格锚更稳 | **未验证** |
| `skill_preset` | 可传 | 官方"技能"预设（疑似特定运镜/玩法模板） | **未验证** |
| `custom_style` / `custom_skill` | 可传 | 自定义风格/技能，可能对应上面两个的自定义版本 | **未验证** |

> ⚠️ **2026-11-21 实测的一个陷阱：网关不校验这些字段。**
> 我用 `style_preset: "__invalid__"` 和 `skill_preset: "__invalid__"` 各发了一条 10 秒任务，
> **两条都 HTTP 200、都正常出片（各 ¥0.20，已记账）。** 说明：
> ① 网关不会因为预设名写错而报错；② 写错 = 静默退化成默认，你永远不知道自己用没用上。
> **所以任何预设参数都必须先做一次"有/无"对照，不能凭"没报错"判断它生效了。**

## 二、这台机器的生成逻辑（从已实测证据反推）

把本技能所有实测结论放在一起，`muse-video` 的真实能力模型是这样一句话：

> **它是一台「连续动作摄影机」，不是剪辑器，也不是动画师。**

四条机制推论，每条都有实测出处：

| 机制 | 证据 | 对写片子的含义 |
|---|---|---|
| **每段独立生成，末帧只是"条件"不是"粘贴"** | 洛阳桥 50s 逐帧核对，40s 边界帧差 36.4（全片均值 9.04），机位被重新构过（`段边界与台词收口.md`） | **多机位快切不可控**。每段会自己重新决定景别，你写的"切到特写"它不一定照做 |
| **只演"当下正在发生的动作"** | 写「桥墩一座座立起」，出来的是两个人站着望江（SKILL 7.5，¥1.20 学费） | **时间流逝、生长、渐变、蒙太奇全部无效**。要么摇镜揭示，要么补拍拼接 |
| **对白由"画面里有没有人在说"驱动** | 5 段都写了台词但每段写「无人开口」，前 30 秒只有环境音（SKILL 九，¥1.00 学费） | **旁白必须写成"持续的男声画外解说"**，且画面里最好别有人正对镜头 |
| **每段 ≤10 秒、一次一个动作闭环** | 平台拆段机制（官方文档 + 50s/60s 实测） | **叙事密度受物理限制**：复杂故事要么拍数多（贵），要么砍 |

**反推出来的适配判据**（这是本节最有用的一句）：

> 一条片子如果**靠"镜头连续运动 + 一个主体持续动作"就能讲清**，Muse 很强；
> 如果它靠**剪辑节奏、文字信息、时间跳跃、多人对话**来讲，Muse 一定拍砸。

## 三、片型适配表

星级 = 用 Muse 做的性价比（★ 越多越该用，★ 越少越该换方法）。

| 片型 | 适配 | 为什么 | 该怎么改 |
|---|---|---|---|
| **产品演示**（一个产品、一组动作） | ★★★★★ | 模型最擅长"手在做什么"；特写、材质、开合都是强项 | 直接用。注意一个靶心（`文案与叙事.md` 第二节） |
| **产品氛围片 / 品牌片**（少台词、靠画面） | ★★★★★ | 一镜到底 + 光照卡统一，正是它最强的组合 | 直接用。旁白压到每拍 20 字以内 |
| **材质 / 微距 / 食物** | ★★★★☆ | 不需要叙事逻辑，只要质感和运动 | 直接用。注意别写"时间流逝"（比如"酱汁慢慢渗进去"可能不动） |
| **动画 / 绘本 / 国风插画** | ★★★★☆ | 风格锚能锁住画风，动作幅度小反而不容易崩 | 直接用。复杂武打、快速转身会崩 |
| **口播 / 知识类**（真人或纯空镜） | ★★★☆☆ | 旁白可控，但**口型是短板**；一次开口 >20 字就开始不同步 | 优先 `mute_voice` + 智凌 TTS 后期配（待验证）；或全用空镜/背影/手部 |
| **剧情短片**（对话驱动） | ★★★☆☆ | 对白由"人在说"驱动，多人同场容易串声 | 拆成**单人对白镜头**；同一时刻只留一路人声；一次开口 ≤20 字 |
| **纪录片 / 历史 / 传说**（跨时间） | ★★☆☆☆ | **不演时间流逝**，编年史式叙事必崩 | 摇镜揭示 + 旁白交代 + 末段补拍拼接（SKILL 7.5 三条替代） |
| **旅行 / Vlog**（多场景快切） | ★★☆☆☆ | 每段重定机位，段间必跳；快切节奏它跟不上 | 压成"一镜到底"，或用叠化吃掉跳变；宁可少场景 |
| **教程 / 步骤演示**（多步骤） | ★★☆☆☆ | 10 秒只能一个动作，五步就要 5 拍 = ¥1.00 | 一步一拍，砍到 3–4 步；或只拍关键一步，其余用图文 |
| **音乐 MV / 卡点剪辑** | ★☆☆☆☆ | **不跟节拍、不会卡点**，生成结果与 BGM 无关联 | 别用 Muse。用素材剪辑 + 后期卡点 |
| **数据 / 图表 / 信息图** | ★☆☆☆☆ | **画不出准确数字和图表**，一定糊 | 别用 Muse。后期包装（AE / 剪映） |
| **需要精确字幕/文字的片子** | ★☆☆☆☆ | 原生不出可读文字，必须 negative 掉 | 画面 mute 文字，字幕全部后期 |
| **真人长台词口播** | ★★☆☆☆ | 口型同步随长度崩，且会自己加词 | 拆短句 + `mute_voice` + 后期对口型 |
| **写实暴力 / 枪械 / 爆炸** | ☆☆☆☆☆ | 官方明说「可能生成失败」，失败退款但白等 7 分钟 | 别用 Muse |

## 四、三个"能救回来"的改造手法

片型不合适不等于做不了，有三招能把不适配的片子拉回可用区：

### 4.1 一镜到底化（救 Vlog / 旅行 / 多场景）

把"切到 A、切到 B、切到 C"改成"镜头从 A 摇到 B 摇到 C"。
**这是唯一能绕开"每段重定机位"的办法**——因为机位变化发生在镜头运动里，而不是发生在段边界上。

### 4.2 摇镜揭示（救时间跨度 / 建造过程 / 变化前后）

**别写"怎么长出来的"，只写"它已经在那儿了，镜头把它摇出来"。**
实测一次就对（洛阳桥：写"桥墩一座座立起"→ 两个人望江；改成"镜头横摇掠过江面，抬到位时远处一座完整的石梁桥横跨江面"→ 桥的形制、桥墩、桥上行人全在）。

### 4.3 拆拍 + 拼接（救"只有末尾一段废了"）

已出片只有最后一段不行时，抽末帧单独补拍 10 秒（¥0.20），ffmpeg concat 拼回去。
比重出整条便宜 6 倍，且不会把已拍好的段落重新随机。

> **新线索（未验证）**：官方说可以传 `reference_videos` 做续写，`duration` 是**成片总秒数**。
> 如果这条路走得通，4.3 就不用自己 ffmpeg 了——但要注意「`duration` 必须比源片至少长 1 秒」，
> 也就是它做的是"把片子变长"，不是"只替换最后 10 秒"。**验之前别改流程。**

## 六、可信度分级

**官方文档（网关 `/api/pricing` description 原文）**：
`reference_videos` 续写规则、`duration` 语义、暴力/枪械可能失败、六个可传参数的名字。

**实测（本技能已有证据）**：末帧是条件不是粘贴、模型不演时间流逝、摇镜揭示可用、
对白由「画面里有没有人在说」驱动、补拍拼接可用、10 秒 36 字舒服。

**本次实测（2026-11-21，¥0.40 学费，已记账）**：
- 网关**不校验** `style_preset` / `skill_preset` 的取值，写错静默退化，两条任务都正常出片。
- 任务状态里有 `metadata.segment / segments / stage`，能看出当前在第几段（比 `progress` 更细）。
- 10 秒档从提交到完成约 1 分钟（这次两条并发，都是 1 分钟内完成）。

**推测（未做对照）**：片型适配表的星级。这是按机制推的，不是拍出来对比过的。
**要改成"实测"，得每个片型真拍一条——不划算，所以标成推测。**

**未验证**：第一节那六个参数的实际行为，一条都没验。
