## 三、分段机制（官方文档原文要点）

- 「按最多 6 段 10 秒生成，每段从上一段的最后一帧接着拍，最后拼成一个 MP4」
- 「时长填 duration（数字）或 seconds（字符串），最多 60 秒，不传就是 60 秒」
- 「时长会平均拆成每段不超过 10 秒，例如 25 秒拆成 9 + 8 + 8」
- 「prompt 写整个视频的内容」
- 「first_image_url 作为第一段的首帧，last_image_url 作为最后一段的尾帧」
- 「参考图会发给每一段，图片合计最多 9 张」
- 「每段需要几分钟，60 秒大约要 18 到 36 分钟」
- 「任何一段失败，整个任务失败并退款，不会单独返回已完成的分段」
- 「队列满了会直接拒绝提交，返回 HTTP 429」
- 「失败的任务会退款。完成后请尽快下载，站点可能在保留期后删除视频」

→ 与旧版的根本差别：旧版只有 10 秒 SKU、`duration` 被忽略；这里是**平台自己拆段续接**，60 秒是真连续。

## 四、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/videos` | 提交，返回任务 id |
| GET | `/v1/videos/{id}` | 状态：queued / in_progress(progress 0–100) / completed / failed |
| GET | `/v1/videos/{id}/content` | 下载 MP4 |

### 请求体

```json
{
  "model": "muse-video-50s",
  "prompt": "……整条片子的内容……",
  "duration": 50,
  "aspect_ratio": "16:9",
  "camera_movement": "缓慢横移，末段升起后退，一镜到底",
  "style": "国风写实电影质感",
  "negative_prompt": "字幕, 水印, 文字, 模糊, 现代建筑",
  "first_image_url": "data:image/jpeg;base64,…",
  "last_image_url": "data:image/jpeg;base64,…",
  "reference_image_urls": ["data:image/jpeg;base64,…"]
}
```

### 响应

```json
{"id": "task_abc123", "object": "video", "model": "muse-video",
 "status": "in_progress", "progress": 40, "created_at": 1762400000}
```

## 五、踩过的坑

- `last_image_url` 必须同时给 `first_image_url`，否则拒绝。
- 图片合计 ≤9 张、单张 ≤10 MB；`data:` URL 可直接用（脚本自动转）。
- 新-api 的 `/api/token/` 接口用 `Authorization: Bearer <sk-...>` 会返回 `INVALID_API_KEY`（那是用户 JWT 的接口），**取密钥只能在网页上点「显示密钥」**。
- 站点余额在顶栏只显示一位小数（¥0.9），真实数字在 `/wallet`（¥10.90），别被顶栏骗了。
- **站点没有公开的余额查询接口**，所以「退款到账」只能靠 `/wallet` 前后对比：
  `muse_video.py refund --id <id> --balance-before A --balance-after B`，差额对不上本单价格就不算退款。
- `429` = 队列满被拒。**不要重试**：这条可能已被受理也可能没有，重试容易变成两条计费。先
  `muse_video.py ledger --refresh` 查账本有没有多出任务。
